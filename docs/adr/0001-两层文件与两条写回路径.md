# ADR 0001 · 两层文件与两条写回路径

- **状态**：已采纳（v1.0.0 起）
- **日期**：2026-10-10
- **影响面**：全部写回行为（新增 / 改写 / 启停 / 删除 / 撤销覆盖 / 漂移处置）

---

## 背景

官方的 `@deepseek-ai/dsh-mcp-client` 是**按行挂载**的：每一个 MCP 服务器对应 `cordis.patch.yml` 里的一行。
本插件的目标是在设置面板里管理这些行，因此必须回答一个核心问题：

> **面板写回时，写哪个文件？**

现实约束有三条（均为实测）：

1. **行有两种来源**：用户**手写**的行（通常嵌在 `- insert: [...]` 里），以及本面板**新增**的行。
2. **官方配置编辑服务（`ctx.configEditor.edit()`）只认顶层 `- id:` 行，且明确排除 `insert` 行**
   （DSH 源码 `packages/boot/config-editor/src/index.ts:117-128`）——
   也就是说，**它够不着嵌在 `insert` 里的手写行**。
3. **`cordis.patch.yml` 写坏 = 下次启动起不来**。这是本 ADR 要避免的头号事故。

## 决策

**分层 + 分道**：

| 层 | 文件 | 谁写 | 覆盖对象 |
|---|---|---|---|
| 真源 | `$DSH_HOME/mcp-manager/servers.json`（`0600`） | 本插件独占 | 受管清单（`mcpx-*` 行） |
| 生成物（自有层） | `$DSH_HOME/cordis.patch.yml`（`0600`，**全量重写**） | 本插件独占 | 受管行 |
| 手写层 | `profiles/<profile>/cordis.patch.yml` | **永不直接改写** | 手写行（经官方通道） |

- **受管行**（id 前缀 `mcpx-`）：写自有层 —— **只写本插件自己生成的内容**，因此**不需要 YAML 解析器**，
  也不存在"碰坏用户注释/缩进"的可能；渲染是**纯函数、确定性**（同输入必同输出，可单测，
  由 `test/store.test.mjs` 直接覆盖）。
- **手写行**：改写与启停**只走官方通道**（`ctx.configEditor.edit()` / `ctx.pluginManager.setPluginEnabled()`），
  因此天然继承官方的**原子写、失败回滚、被更高层覆盖则拒写**三条语义。官方通道的写入落点就是 profile patch ——
  由此产生了"覆盖行"这一现象，见 §后果。

## 被否决的替代方案

| 案 | 内容 | 否决理由 |
|---|---|---|
| **A** | 面板**直接改写** `profiles/<profile>/cordis.patch.yml`（自己实现插入/删除） | ① 需要自带 YAML 解析器与保序重写，**一旦写坏宿主起不来**；② 与官方编辑服务争夺同一文件的所有权，会互相打架；③ 无法自然获得官方的回滚与"被覆盖则拒写"语义 |
| **B** | 把手写行**也搬进自有层**（统一由本插件管） | ① 所有权冲突：那是用户手写的配置，面板擅自迁移等于越权；② 迁移需要解析现有内容，回到 A 的问题；③ 用户后续手工编辑会与自有层不一致 ⇒ 产生第二种"漂移" |
| **C** | 手写行**不提供改写**，只做只读展示 | 能力过窄：实测中最常见的需求恰恰是"改一条手写行的 url / env"，只读面板会被绕过（用户改回手工编辑），失去护栏意义 |
| **D** | 用文本替换（正则/字符串）**就地改**手写行 | 行内可能有注释、引号风格、多行标量；文本级改动无法保证只动目标字段，且**没有回滚** |

## 后果

1. **需要"漂移检测"**：自有层是生成物，一旦被外部改动（含换行符变化）就与清单不一致 ⇒
   生成物里写入 `managed-by` 标记与 `# rev: <sha256>`，哈希不符即**面板转只读**并给出两个逃生口
   （以清单为准重建 / 以文件为准清空清单）。
2. **"覆盖行"成为既定行为**（官方通道的落点决定）：
   首次改写某条手写行 ⇒ 官方在 profile patch **末尾追加一条顶层覆盖行**；之后同 id **原地更新**。
   于是必须让用户看得见、可回退：面板标注 `已覆盖` 并提供「**撤销覆盖**」
   （调用官方语义：`next === inherited` 时移除覆盖行）。
3. **一条容易被误读的后果必须写进文档**：**已被覆盖的手写行，再改 `insert` 行不生效**（被覆盖行压住），
   需先「撤销覆盖」。
4. **乐观锁成为必需**：两个浏览器窗口同时操作会互相静默覆盖 ⇒ 除 `state`/`list`/`heal` 外，
   所有写方法接受 `expectedRev`，不匹配即 `stale-revision`。
5. **手写行不可删、不可改标识与协议** —— 这不是本插件的取舍，而是**官方编辑服务的能力边界**。
